# Guía y recepción de devoluciones

El panel contextual de Devoluciones incorpora registros de guía y recepción dentro de la comparación oculta, con textos en español e inglés. Las rutas nuevas devuelven 404 fuera de comparación. El módulo, navegación y controles actuales se conservan.

La guía almacena transportadora y número de seguimiento declarados por un miembro autorizado. No compra ni genera una etiqueta, no consulta una transportadora y no acredita entrega o aceptación externa. El registro de recepción conserva referencia, cantidad total declarada, estado, observación, hora declarada y momento de registro. La interfaz declara la recepción al guardar. Una integración autorizada puede registrar una hora ISO con zona, posterior a la apertura y sin más de cinco minutos de adelanto; se conserva la diferencia entre hora declarada y hora de registro.

Registrar recepción marca el caso como recibido en la misma transacción y utiliza el historial de decisiones actual. Mantiene la nota de resolución. La cantidad no se presenta como cotejo automático con las líneas del pedido y el estado recibido no constituye aprobación de reembolso. Este incremento no ejecuta dinero, mensajes, reposiciones ni crédito de tienda. Esas acciones siguen usando los servicios de postventa y aprobaciones existentes.

La tabla privada es inmutable para clientes y para escrituras directas del rol de servicio. Las RPC exigen actor real, permisos actuales de Devoluciones y, cuando corresponde, Bandeja y propietario del buzón personal. Comprueban negocio, contacto y conversación coherentes. Las escrituras bloquean la ficha y permisos relevantes, requieren suscripción con escritura y solo admiten casos locales aprobados o recibidos. Las devoluciones gestionadas por otra plataforma continúan siendo de lectura.

El identificador de operación evita duplicar un registro si se pierde la respuesta. El mismo actor puede recuperar su resultado idéntico después de cambiar el token o la suscripción; primero se vuelven a comprobar visibilidad y permisos. Reutilizar el identificador con otros datos, actor, caso o negocio produce conflicto. Un registro nuevo exige el token exacto de actualización. Cada evento avanza ese token y queda ligado al actor real. Un fallo de auditoría revierte también la recepción y el estado.

El lector utiliza una página privada de veinte eventos ordenados por secuencia, con cursor estable incluso si coinciden las horas. La interfaz consulta al abrir, cancela al cerrar o salir y acota el historial mostrado a cien registros. Cada caso admite hasta quinientos eventos. No devuelve notas de cliente, fotos, nombres o credenciales en este historial nuevo. La eliminación autorizada de una ficha o cuenta elimina sus eventos mediante las claves externas; no se añade una retención perpetua.

No hay llamadas de IA adicionales ni cambios de precio. Las pruebas usan PostgreSQL aislado, sesiones y proveedores sintéticos. La evidencia humana no se sustituye por un mensaje del cliente, una respuesta del modelo o un estado externo supuesto. La generación automática de etiquetas y la recepción confirmada por una transportadora requieren un contrato de integración comprobado por cuenta.
